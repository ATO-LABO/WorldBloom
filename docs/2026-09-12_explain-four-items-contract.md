# 四項目（選択・根拠・代償・転機）の表示契約

## 0. この文書の位置づけ

同じ設定と結末に到達した候補どうしを比べるとき、変化度と種類の表だけでは「物語がどう違うのか」が読み取れない。各候補について「**誰のどの選択が、何を根拠に行われ、何を失い、どう次の展開につながったか**」を、ログで裏づけて表示するための契約を定める。

本文書は後続カード（002 記録・003 抽出・004 画面・005 検証）の入力であり、006 の要否判断の根拠でもある。`docs/2026-09-11_gapengine-detailed-design.md` の §14 出力段とは別系統で、あらすじ・本文の生成（`gapengine/scenes.py`・`synopsis.py`）には手を入れない。

## 1. 監査結果

対象は `runs/exp10-detective`（探偵）と `runs/exp7-romance`（恋愛）。以下はすべて実ログの実測であり、推定を含まない。

### 1.1 四項目の裏づけ

| 項目 | 記録の所在 | 判定 |
|---|---|---|
| 選択（実行した行動） | `decision` 行の `subject` / `verb` / `args` / `result` / `choice_prob` | 出せる。**旧ログでも出せる** |
| 選択（選べた別行動） | 記録なし。候補集合は選択の直前に生成され、書き出されずに捨てられる | 記録の追加が要る |
| 選択（どの状況で） | `decision` 行に `zone` が**無い**。移動イベントと日次 `snapshot.layers.zone` から復元は可能 | 記録の追加が望ましい |
| 根拠（選択要因） | `decision.policy` の `m_cat` / `m_nov` / `m_risk` / `m_stance` / `p_prec` / `ctx` / `effective_genome` | **主人公のみ**。脇役は 1 件も無い |
| 根拠（当時の知識） | 日次 `snapshot.layers.valued_beliefs` と `belief`、`learn_fact` / `rethink` イベント、`delta.actor` | 出せる（§1.2 で検証） |
| 代償 | `decision.delta` の `relations` / `actor` / `targets` / `objective` | 出せる（即時分のみ。§2.4 で線引き） |
| 転機 | 上記の状態変化と後続行動の候補条件から判定できる（§2.5） | 判定規則を新設 |

脇役の選択要因が無い件は、同一ランで主人公 29 件に対し他 5 主体の計 145 件がすべて欠落している。ただし Astra R2 により、**脇役に方針を与えることは求められていない**。脇役については行動と結果を説明に含め、選択要因は「不明」とする。

### 1.2 決定直前の知識復元の検証

当初は日次スナップショットとの照合（40 ラン 219 日、219/219 一致）で足りると判断したが、これは**日末の状態**しか保証しない（Astra R3）。決定の直前を検証するため、エンジン自身のゲートを使った独立検証を行った。

`confront` は決定時の信念でゲートされる（`engine/verbs.py`: 信念が無ければ `belief_unavailable`、値が対象と異なるか確信度が `act_threshold` 未満なら `belief_below_threshold`）。したがって、決定行より前の行だけから復元した信念がこのゲートの成否を再現できれば、復元は決定時点で正しい。

120 ランで測定した結果は次のとおり。

| 判定 | 件数 |
|---|---|
| 復元とエンジンのゲート判定が一致 | 130 |
| 不一致 | **0** |
| ゲート以前（前提エッジ・対象不在）で弾かれ対象外 | 68 |

同日内の順序と、決定直後に得た情報を遡って使っていないことは、この検証に含まれる（復元は決定行より前の行のみを適用するため）。

### 1.3 `delta` の意味が項目ごとに違う（実装の落とし穴）

`decision.delta` は名前に反して、内容が統一されていない。

| 場所 | 記録されている値 |
|---|---|
| `delta.relations` | **変化量**（`Relations.change` の戻り値。例 `affinity: -0.2`） |
| `delta.actor` / `delta.targets` | **変化後の値**（例 `resources.reputation: 0.15`） |

実測: ある候補で `confront` が誤認に終わった決定（T11）の `delta.actor.resources.reputation` は `0.15`。コード上この行為は評判を `-0.1` するもので、直前の日次スナップショットは `0.25`、直後は `0.15` だった。つまり **`0.15` は結果の値であり、増加量ではない**。

この差を無視すると、評判が 0.10 下がった出来事を「0.15 の増加」と表示してしまう。**行為者の資源の損失は `delta.actor` から直接読めない**。直近のスナップショットとそれ以降の `delta.actor` を追って前の値を復元し、差を取る必要がある。

## 2. 四項目の契約

### 2.1 連結の規則（最重要）

四項目を**別々に拾って並べてはいけない**。ひとつの候補について、次の連鎖をひと組として選ぶ。

```
ある選択 ──(その決定の delta)──→ 代償
   ↑                                  ↓
 根拠（決定直前の状態）        後続で条件が反転 → 転機
```

代表となる組の選び方は次の順で決める。

1. その候補で**確認済みの転機**（§2.5）を列挙する。
2. 各転機について、それを生んだ上流の選択を特定する。転機が状態変化を伴うイベントなら、その状態変化を起こした決定が上流の選択。
3. 上流の選択が複数あるときは、結末への到達に条件として効いたものを優先する。
4. 選ばれた組（選択・その根拠・その代償・その転機）を 1 件として提示する。確認済みの転機が無い候補では、代償が最大の選択を中心に据え、転機は「候補」または「該当なし」とする。

各項目を独立に最大値や先頭行で拾うことは禁止する。どの出来事を代表に選んだかは出典とともに追えるようにする。

### 2.2 選択

出すもの: 誰が、どの状況で、何をしたか。状況は決定直前の場所と同席者。

選べた別行動は、記録がある場合のみ併記する。記録が無い旧ログでは、**実行した選択は「確認済み」、代替候補だけを「不明」**とする（Astra 003-R3）。候補集合を一部しか記録していない場合、記録件数・総候補数・省略の有無・選別規則を併記し、**部分集合を「全選択肢」として表示しない**。

### 2.3 根拠

二つを分けて出す。

- **選択に関与した情報**: その行動が候補に立つ条件と、実行時の判定が実際に読んだ状態。verb ごとに定まる（付録 A）。例: `confront` なら対象への信念の値と確信度、`act_threshold`、前提エッジ `observed` の充足。
- **当時知っていたこと**: 決定直前に本人が保持していた信念・知識のうち、上記に含まれないもの。

表面には短い説明を出し、乗数（`m_cat` ほか）と確率は詳細の証跡に置く。**心理的な動機に変換しない**。「重み付き抽選の結果」を「正義のため」と書くことを禁じる。

脇役については「選択要因は未記録」と明示する。

### 2.4 代償

**`delta` の実変化すべてが代償ではない**（Astra 003-R2）。行為者にとっての損失に限る。

前提として、コードには「損失・利得・狙いどおり」を区別する汎用の項目が存在しない。`risk` フラグは「対象に何かする行為か」を示すだけで、誰の損失かまでは表さない。`stance_sign` は付与されるだけで実行側から参照されていない。したがって**代償の判定は verb ごとの表（付録 A）で定める**。汎用の推論では出さない。

共通の原則は次のとおり。

| 扱い | 条件 |
|---|---|
| 代償として出す | 行為者の資源（`reputation` / `bonds` / `stamina`）が**減った**場合。§1.3 のとおり前の値との差で判定する |
| 代償として出す | 行為者が関わる関係の悪化。方向は verb により異なる（相手から行為者への好意が下がる場合と、行為者から第三者への好意が下がる場合の両方がある） |
| 代償として出す | 行為者が手放した所持物（`give_item` の対象、`grand_gesture` の資産） |
| **出さない** | 相手の能力・資源の低下（`neutralize` の無効化など、狙いどおりの効果） |
| **出さない** | 行為者側の増加 |
| **出さない** | 同じ決定の `delta` に含まれない、直後に起きただけの変化 |

遅延した代償（「味方を失ったせいで後から困った」）は記録が無い。**未確認であることを明示し、「代償なし」と書かない**。

### 2.5 転機

Astra R4 に従い、二段階にする。

- **転機候補**: 再考・誤認・露見・裏切り・伏線回収・結末・戦闘不能・復帰など、該当種別のイベントが起きた場面。現在ビューアが付けているタグはこれにあたる。
- **確認済みの転機**: 状態変化の前後で、**後に実際に起きた行動の候補条件の成否が反転した**もの。反実仮想の全探索は行わない。実際に起きた行動だけを対象にする。

時間順に並んでいることは因果の証拠にしない。

## 3. 三値と出典参照

抽出側は各項目について次の 3 値を明示的に返す。推測で埋めない。

- **記録上確認できる**: 出典となるログ行がある。
- **該当する出来事がない**: 探索した結果、条件に合う出来事が存在しない。
- **記録不足で不明**: その情報が記録されていない（旧ログの候補集合、脇役の選択要因など）。

出典参照は「実験名 / セル / ラン（`layers_path`） / ターン / 行の位置」で表す。イベント ID は存在しないため、ラン内の行位置を安定した参照とする。

## 5. 002（記録の追加）への確定事項

1. **候補集合**を記録する。上限は重み上位 8 件。**実際に選ばれた行動は上限に関わらず必ず残す**。総候補数・記録件数・省略の有無・選別規則を同じ行に併記する。残った件数で確率を再正規化しない。保存用の並べ替えで実際の候補配列や選択順を変えない。
2. **決定時の場所**を `decision` 行に加える。
3. 脇役への方針の追加は**行わない**。観測の追加と意思決定の変更を混ぜない。
4. 既定は無効（互換モード）。固定ハッシュ 2 本とアーカイブのバイト互換を守る。ただし**新しい説明を生成する通常の導線では有効にする**。出力に設定と記録範囲を書き、利用者が常に「記録不足」の画面を見る仕様にしない。
5. 過去 16 実験は再実行しない。説明が必要な候補は、同一シード・同一遺伝子で記録を有効にして再実行する（決定論により同じ経路が再現される）。再実行したことと元のランとの対応を出力に残す。
6. 検証は、追加フィールドを除いた既存フィールドが同一シードで一致すること。

## 6. 006 の要否

**現時点の判定は「要否未確定」**（Astra の指摘どおり、「不要」と確定しない）。

判断は三段階で行う。

- **002 記録**: §5 の 6 項目。対象は候補集合と場所の記録のみ。
- **003 抽出**: §2 の契約と §3 の三値。転機判定はビューアの実装を抽出側へ移して共有し、ビューアが抽出側に依存する向きにする（逆流させない）。`scenes.py` と `synopsis.py` は変更しない。

## 付録 A: verb ごとの選択条件と代償

`engine/actions.py` の候補関数と `engine/verbs.py` の実行メソッドから抽出。003 の実装時にコードと再度突き合わせる。

| verb | 選択に関与した情報（候補条件と実行時の判定） | 行為者の代償 |
|---|---|---|
| `move` | 到達可能な経路、`stamina`、道に必要な道具の所持、目的物の所持と目的地、同行者の stance | `stamina` の減少 |
| `observe` | 相手の隠れた修飾子の有無、既知の修飾子、身元を見たか、誤情報を受けているか、permission | なし |
| `investigate` | 現在地が調達地か、不足しているレシピ材料、`curiosity` / `diligence` | なし |
| `neutralize` | 相手の active な修飾子のうち**自分が知っているもの**、前提エッジ `known_modifier`、permission | 相手から行為者への好意 −0.2。**誓約中なら裏切り**として評判 −0.5 と、その場の立会人から行為者への好意 各 −0.3 |
| `confront` | 対象への信念の値と確信度、`act_threshold`、前提エッジ `observed`、世界の真値の有無 | 正解時: 相手から行為者への好意 −0.4。誤認時: 評判 −0.1 と相手から −0.3、さらに自分の確信度が半減 |
| `rethink` | 保持する証拠（implies / refutes を持つ事実）が 2 件以上、直近の新事実からの停滞スロット数 | なし |
| `share_knowledge` | 相手が未知の事実、`share_min_affinity` と現在の stance、`secrecy`、permission | なし（双方の好意が上がる） |
| `give_item` | 所持品のうち目的物・レシピ・乗り物・形見を除いたもの、相手のレシピ知識、permission | **対象の所持品を 1 つ失う** |
| `pledge` | 双方向の stance が 0.4 以上、未誓約であること、permission | なし（相互に好意 +0.15） |
| `payoff` | 回収可能な保留効果の有無 | 効果の内容による（`engine/phase2.py`。003 で確定） |
| `persuade` | permission のみ（信念等の条件なし） | なし |
| `mislead` | 自分の強さの虚偽値、または自分が持つ価値ある事実の真値以外の値、permission、相手の頑固さによる信頼ゲート | なし（この行為自体は関係を変えない） |
| `grand_gesture` | 差し出せる資産の所持、相手の既知の「傷」にあたる事実、permission | 資産 1 つを失う。**その場にいる他の味方への好意 −0.2**（評判は +0.1 で上がる） |

補足。`mislead` は `stance_sign` が −1 でありながら、実行側で関係を変えていない。誘導が露見するのは後の `observe` による誤情報の解除であり、そこまで含めて因果を追う必要がある。

## 付録 B: 前提エッジの語彙

`engine/world.py` の `prerequisite_ok` が実装しているのは 3 種類のみ。

- `known_modifier`: 行為者が対象のその修飾子を知っていること
- `observed`: 行為者が対象の身元を見たか、何らかの修飾子を知っていること
- `pledged`: 両者が誓約関係にあること

これ以外の値は**常に不成立**として扱われる。テンプレートで未対応の語を書くと、その行動は黙って候補から消える。

## 付録 C: 候補集合の所在（002 の実装位置）

- **生成**: `engine/actions.py` の `candidates()`。各 `_<verb>_candidates` を集約し、重みが 0 より大きく、許可された verb で、ジャンルが許すものだけを名前順に並べて返す。
