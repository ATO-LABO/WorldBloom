## F1 [P1] 所持品の喪失が「不明」に落ちる（契約の最優先カテゴリが発火しない）

対象: `gapengine/explanations.py` の `_cost`。

```python
prior = _get(before, path) if path[0] != "stamina" else None
if after is None and prior is not None:
    after = 0  # deletion of a recorded asset, not an unknown baseline
```

`engine/log.py` の `nested_diff` は「`after` にキーが無い＝削除」を `None` として書く（L21〜23）。したがって `delta.actor.resources.assets.X: null` は「持っていたものを失った」ことの**完全な記録**であり、直前値の復元を必要としない。ところが実装は `prior is not None` を条件にしているため、復元側が直前値を持っていないと確定した代償を「不明」に落とす。

再現条件（`C:\Projects\WorldBloom-local\runs\exp7-romance\g3\ind-92\seed-0\layers.jsonl`）:

| 行 | 決定 | 結果 | 理由 |
|---|---|---|---|
| L21 | A の T4 `give_item D 手紙` | **unknown** | A の初回スナップショットは L26。開始時の所持品は記録されない |
| L58 | C の T9 `grand_gesture B` | **unknown** | C は脇役でスナップショットが無い |
| L97 | A の T16 `give_item D 花束` | confirmed | 直前のスナップショット L52 に `花束: 1` がある |

影響: スナップショットを持たない脇役は resources 系の代償が**常に**不明。主人公も初回スナップショット前は不明。契約 §2.4 が最優先に置く「手放した所持物」がほぼ発火しない。依頼の探偵例「協力者からの信用を失う」に対応する機構を 001 で見つけておきながら、表示段で落としている。

修正案: `resources.assets.*` の `after is None` は `prior` に関わらず確定した代償として扱う。数量が不明なだけで喪失は確定しているので、表示は「所持品 手紙 を失った」でよい（数値を出さない）。`reputation` のような数値は baseline が無ければ差を取れないので、不明のままが正しい。

## F2 [P1] 転機の三値が契約 §3 と食い違い、画面が自己矛盾している

対象: `gapengine/explanations.py` の転機フィールド生成と `viewer/explanation_ui.py` の `entry()`。

実際の描画:

```html
<dt>転機 <span class="tag">不明</span></dt><dd>転機候補</dd>
```

契約 §3 の対応表は「転機候補（該当種別のイベントはあるが反転を示せない）→ **記録上確認できる（候補として）**」と定めている。実装は `field(UNKNOWN, "転機候補", confirmation="candidate")` を返すため、記録上はっきり存在する再考が画面では「不明」と表示される。ラベルと本文が矛盾している。

あわせて、転機に `absent` を返す経路が存在しない。生成は `field(UNKNOWN, ...)` か `attach()` の `CONFIRMED` のみで、契約 §3 の「該当種別のイベントが無い → 該当する出来事がない」は到達不能。実測でも探偵 168 決定で unknown 167 / confirmed 1 / **absent 0**。依頼本文が求める三区分のうち、転機だけ二値に縮退している。

修正案: `confirmation` と `status` の対応を契約 §3 の表どおりにする（candidate → confirmed(候補として)、該当種別のイベントが無く探索範囲を走査済み → absent、判定未対応・記録不足 → unknown）。画面のタグも `confirmation` を反映させ、「確認済み」と「候補」を見分けられるようにする。

## F3 [P2] `move` の stamina 代償が常に不明。002 が直前値を記録していれば確定できた

`_cost` は stamina の `prior` を意図的に `None` にしている。受動回復（`engine/sim.py:_recover_stamina`）が決定の delta に出ないため、スナップショットの値を直前値として使えないという判断で、これ自体は妥当。

しかし結果として、付録 A が「確定した代償: `stamina` の減少」と書く `move` が全件「記録不足または判定未対応」になる（探偵 23/31、恋愛 20/26 がこの理由）。契約と実装が正面から食い違っている。

002 は `zone` と `present` を記録したが、行為者の**決定直前の resources / stamina** は記録していない。契約 §1.3 が「直近のスナップショットとそれ以降の `delta.actor` を追って前の値を復元する必要がある」と名指しした値が、復元不能なケースで記録されないまま残っている。記録を足す工程は 002 であり、そこで拾うのが筋。

どちらかに寄せる判断が要る。

- (a) 002 に決定直前の `stamina`（できれば `resources` も）を加える。F1 の脇役ケースも同時に解消する。記録量は増える（現状で 2.46〜2.71 倍）。
- (b) 付録 A の `move` を「判定未対応」に改訂し、契約側を実装に合わせる。

推奨は (a)。理由は、F1 と合わせて「誰が何を失ったか」という依頼の中心が、脇役と序盤で恒久的に不明になるのを避けられるため。

## F4 [P3] 根拠の status が「確認済み」だが、不完全であることが画面に出ない

`grounds` は `complete=False` を常に持つが、`panel()` は `status` のタグしか出さないため「根拠 確認済み」と表示される。「決定前に記録された知識」であって「この選択に効いた情報」ではないことは muted の注記にあるが、**知識の一覧が部分的である**ことは詳細 JSON の中だけにある。Astra 自身が引き継ぎで「取得済みの知識は部分的な記録であり、知識の完全な一覧とは主張しない」と書いているので、1 行の注記を表に出せば足りる。
