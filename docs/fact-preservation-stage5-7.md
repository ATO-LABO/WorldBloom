# 事実を保つ文章生成：段階5〜7

段階1〜4の実装記録は `fact-preservation.md` と以前の成果物に残す。
ここでは新しい実行からの記録生成、通知・認識・行動の実行確認、作者向け画面を追加した。
基点は develop `52a456408d5ec8c534b7de9d49892b019c06fd78`。

## 段階5：新しい実行から補助資料へ

実際の `Simulation` / `CalendarRuntime` に任意の `fact_model` を追加した。
これがない既存の世界では、通知・認識・状態形式を追加しない。
新しい実行は既存の実行記録に `details.fact_record` を併記し、段階3の抽出器へ渡す。
保存済みの旧ログを補正したり、旧記録を新しい意味に読み替えたりしない。

主張、到達、気づき、理解、認識、行動候補、選択、開始、結果、状況、合意を区別する。
参照の物理行とSHAは、従来どおり補助資料に持たせる。
主体名は日本語を許可する。保存パスに使う記録ID・パッケージIDは従来の制限を維持する。

既存のcalendar世界を生成ジョブへ固定する際は、公式ローダーで検証した宣言済みの人物一覧を保存する。
プロジェクト直下の人物ファイルや `execution-version.json` も含め、無関係な旧テンプレートの行動グラフを注入しない。

## 段階6：通知・認識・行動を実行する

入力には全人物の端末利用、移動中の読取・送信可否、読取・送信時間を明示する。
送信完了後に主張が生まれ、指定した遅延後に到達する。気づきの指定時刻は到達後にだけ適用する。
端末が使えない場合は気づきも読取も発生しない。気づいただけでは理解や認識を更新しない。
実際の読取完了で理解記録と人物の知識を更新する。

認識は到着予測・理由評価・意図推測を分ける。更新には理解済みの主張、更新前後、規則版を残す。
明示していない意図推測は生成しない。同じ連絡を分割した主張は、同じ人物・領域・述語の独立した追加根拠として重複適用しない。
口論は状況記録であり、通知に気づくかどうかを自動的に決める規則にはしない。

`move_and_send` / `move_and_read` は許可された場合に実移動と実連絡を同じ時刻に開始する。
終了時刻は各処理の所要時間による。候補を出したことと、選んだこと、実行したこと、結果は別記録に残す。
既存の一般行動候補は実行時に可否を確定するため、候補段階の `feasible` を不明として残す。
チェックポイントでは実行中の連絡・理解・認識・適用済み根拠を保存し、再開時に記録との整合を検査する。

試走の時間値・認識更新値・規則は作者が明示した検証条件である。
確率モデル、心理推定式、作品用の既定値、自律的な行動選択を新たに決めたわけではない。
現行の明示コマンドを実行する仕組みに接続した検証であり、通常の自律プレイの品質受入れとは区別する。

## 段階7：書き方を編集し、保存して生成する

素材画面から「場面の文章化」を開く。
採用・必須・非開示・視点と、あらすじ用／本文用の書き方を別々に編集する。
共通の事実保持条件は閲覧専用。限定的な矛盾検出に該当する指示は保存・生成を拒否する。
プレビューは選択された可視入力と実効プロンプトを表示し、生成ジョブや保存履歴を作らない。

編集は下書きとして保持し、保存前の下書きから生成させない。
保存は追記式の不変版とSHA付き親参照で管理する。同じ版を前提とした競合保存は拒否する。
既定値に戻す操作は下書きだけを変更する。旧版は閲覧専用で残り、旧生成結果を変更しない。
生成受付後は既存のジョブ進捗画面を開き、準備中の出力未作成を欠落と表示しない。

生成結果は実際に使った書き方、可視入力、プロンプト、モデル設定、応答、検査結果に結び付く。
あらすじの引継ぎは同じ原記録・選択・開示範囲を照合し、本文へ固定記録も渡す。
現在の編集内容を変えても、過去結果の画面は当時の固定内容を表示する。

新経路 `facts_v1` は終わっていない場面も扱う。旧 `story_v1` の結末必須・到達済み／採用条件は維持する。
新しい場面のためにSiftingの到達や採用状態を偽装しない。

## 検証と未検証

固定応答は使い捨ての検証用runtimeのtransportにだけ設定する。
実際のジョブ受付・準備・別プロセス実行・保存・結果表示を通し、外部モデルは呼ばない。
形式と型付き対応記録が一致しても、文章の意味は未検証、利用者の採否は未決定と表示する。
実モデルによる忠実性・漏えい・読みやすさ・作品の魅力の評価は段階8に残る。

Windowsで実測した一時的なファイル置換拒否には、calendar状態と共通JSON保存の置換だけを最大6回再試行する。
置換まで旧完全ファイルを保持し、継続する拒否や他のエラーは失敗として返す。
初回失敗ログを残し、修正後の結果とは分ける。OS側の拒否の具体的原因は特定していない。

## 生成と状態復元の境界修正

workの選択記録は、同じverbだけでなくtask_idも一致する候補へ結ぶ。候補から選択への参照を読み込む際も、対象の一致を検証する。表示された候補と実行した作業の根拠が異なる記録を受理しない。

通信中の復元では、開始・完了イベントから未完了の通信を復元してcommunicationsと照合する。通信一覧の欠落や、イベント履歴と異なる内容を拒否し、拒否した場合は実行中の状態を変更しない。外包SHAを更新しないファイル破損の検査は、従来のチェックサム層が担う。

場面生成の受付応答を失った場合、同じタブでは保存済み版・入力SHA・生成種別に結び付けた要求IDを保持し、再クリックや再読込みでも同じ要求を使う。受付済みジョブが完了していても、確認操作で別の生成を開始しない。受付を確認できた後の意図的な生成と、新しい保存版の生成は別の要求IDを使う。タブを閉じた後や別端末への要求IDの引継ぎは、この修正の対象に含めない。

回帰テストはchoose-headlineの実行・誤った候補参照の拒否、読取中の通信一覧欠落と正常再開、HTTP受付応答だけを切断した後の再送を扱う。UIコントローラーの検査はPythonのオフライン試験からNode.jsを呼び出す。実モデルは使用しない。
