# 共同行動と共同作業の使い方

[設計書](joint-activities-design.md)を、共通の実行処理と目的からの計画探索へ接続しました。共同移動と共同作業は同じ予約・合意・時間管理を使います。人物はそれぞれの目的、優先順位、譲れない条件、知識を保ちます。

## 世界と人物の設定

世界設定の `joint_activities` に `version: 1`、`definitions`、`workflows`、`instances` を指定します。項目がない世界は従来の処理を使います。

| 項目 | 定義するもの |
|---|---|
| definitions | 行動の種類、役割と人数、必要な知識・行動権限、所要時間、道具や材料、体力消費、効果 |
| workflows | 作業の工程、依存関係、必要な作業量、成果物、最後に変える状態 |
| instances | 今回の対象、参加者と役割、合意内容のバージョン、開始できる期間、提案を受け取った人物 |

目的と優先順位は既存の人物設定の `commitments` に置きます。同じ目的を全員に追加する処理はありません。渡航の例では、各人物が全員の到着を大切にする設定を明示しています。

実際に読み込める入力は次の例の `world.yaml`、`subjects`、暦を使う場合の `contract.yaml` にあります。[設計段階の契約例](design-examples/joint-activities-contract.json)は全体をそのまま世界設定へ入れる形式ではありません。

## 実行例

| 例 | 確認すること | 実際の経過 |
|---|---|---|
| [桃太郎の渡航](../projects/joint_voyage_example/world.yaml) | 各人物が目的から参加を選び、一隻を共有する | 朝に返答し、昼に出航、夕に全員が到着する。操船者の体力消費は2、同乗者は0 |
| [宇宙船の設備修理](../projects/joint_repair_example/world.yaml) | 個人作業、情報の引き継ぎ、共同作業、確認をつなぐ | 08:00〜08:10に診断し、08:11〜08:12に内容を伝える。二人で08:12〜08:32に交換し、08:37に動作確認まで終える |
| [文化祭の展示制作](../projects/joint_festival_example/world.yaml) | 人物、工程名、対象、最後の状態を替えて同じ処理を使う | 設計、二人での組み立て、点検を進め、08:37に展示の確認を終える |

修理と展示制作は、担当者と初期の合意を明示した実行検証用の例です。情報共有には既存の `share_knowledge` を使い、作業が終わっただけで次の人へ診断内容を渡す扱いにはしません。渡航の例は参加の返答を初期入力で確定させず、共通の目的評価から選びます。自動で参加を選ぶ暦の例と、保存後の再開も試験で確認しています。

リポジトリ直下で次のように実行できます。出力先には新しいフォルダか空のフォルダを指定してください。既存の記録がある出力先への再実行は拒否し、上書きしません。モデルや外部APIは呼び出しません。

```powershell
python scripts/run_joint_examples.py --out runs/joint-examples
```

一つだけ実行する場合は `--example voyage`、`--example repair`、`--example festival` のいずれかを指定します。各出力先の `layers.jsonl` が原記録で、`joint-report.json` に区間、負担、成果をまとめます。

## 合意と開始

行動定義には登録済みの `joint_move` または `joint_work` を指定します。自由記述の命令や任意の式は実行しません。役割ごとの必要人数と資格を確認し、同じ人物を二人分には数えません。

提案には対象、役割、時間、資源、負担を結び付けた識別値を持たせます。違う内容への古い合意は使えません。返答は実際に届いた人物だけが知り、未受信の返答を計画の確定事項にしません。初期合意を使う場合は `authored_initial_terms`、合意した人物、内容を知る人物を明示します。

合意後は全員と資源をまとめて予約し、開始時に所在、権限、知識、体力、個人の条件、材料を再確認します。一人でも条件を満たさなければ、全員の開始を中止し、開始費用を取りません。競合する候補は参加者の優先順位で比較します。

現在の実装では参加者と役割の組を設定で提示します。未知の人物を探して勧誘し、編成を一から作る処理は追加していません。合意済みの例で移動を確認することと、本人が目的から参加を選ぶことは別々に検証します。

## 時間と負担

所要時間は正の整数で、単位は `logical_step` または `minute` です。開始を含み終了を含まない区間として全員の時間を確保します。単位を暗黙に変換せず、観測期間を越える行動は開始しません。

共同実行中の人物は別の個人行動を始めません。同乗者の体力消費を0にしても、その時間を別の作業に使うことはできません。移動中には実際の航路上の場所を持ち、到着時に全員の位置をまとめて変更します。別の船の内部を、同じ航路にいるという理由で観測できる扱いにはしません。

作業量は `fixed_group_rate` または上限を指定できる `sum_role_rates` で計算します。前者は集団として一定の速さで進むため、二人で20分作業しても、毎分1なら作業量は20です。役割別の体力消費は別々に計算します。

暦の既存作業へ接続する場合は、その作業記録と材料を使います。共同管理へ接続した作業を、従来の個人作業の加算処理へ重ねて渡しません。約束の履行には実際に完成した作業と人物ごとの寄与を既存の判定へ渡します。

## 中断と引き継ぎ

参加者、役割、合意内容は実行区間が始まった後には変更しません。離脱した場合は区間を閉じ、成果を残します。代役は新しい合意と新しい区間で残量を進めます。

試験では12分目に交換を始め、19分目に中断した時点の進捗7と、役割別の負担0.7、0.35を保持することを確認します。新しい担当者は残量13だけを進めます。診断内容を受け取ったかどうか、対象と入力のバージョンが適合するかも確認します。

開始時に使った材料は中断で戻しません。完了時に使う材料と完成品は一度だけ処理します。物語内の事故で発生した結果は残し、実装上の例外では処理途中の書き込みを戻します。

## 保存と表示

通常ターンの共同実行には `snapshot` / `restore` があり、共同区間、予約、進捗、費用、関係する人物の実際の状態を復元できます。通常ターンのシミュレーション全体へ新しいディスク再開機能を追加する変更ではありません。暦の実行では既存のディスク保存・再開へ統合し、別の実行環境から再開した原記録が連続実行と一致することを確認しています。

「目的と計画」では共同行動を一つのまとまりとして表示します。開くと役割別の負担、開始・完了時刻、作業の残量を確認でき、経過から原記録へ進めます。共同作業の完了と各人物の目的の達成は別の判定です。

## 検証の範囲

実行処理の試験は [test_joint_activities.py](../tests/test_joint_activities.py)、[test_joint_calendar.py](../tests/test_joint_calendar.py)、[test_joint_acceptance.py](../tests/test_joint_acceptance.py) にあります。[設計時の受入条件](joint-activities-acceptance.md)に沿って、通常ターンと分単位の実行、個人行動との競合、知識、優先順位、中断、成果、復元を確認します。

別題材で同じ処理が使えることと、読者にとって物語が面白いことは別の評価です。この変更で確認するのは、人物の判断と実際の共同実行が矛盾せず接続することです。
