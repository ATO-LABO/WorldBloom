# 共同行動と共同作業の設計

## 設計の範囲

複数人が同じ工程を同時に実行する仕組みと、複数人が時間を分けて進める作業を、既存の目的評価・時間管理・作業管理へ接続する設計案です。共同移動と設備修理の両方を初期の対象にします。今回は設計書、契約例、受入条件を定め、実行エンジンの変更は次の実装段階で行います。

参加者はそれぞれの目的を持ち続けます。主催者の計画が他人の受諾を確定させることはありません。勧誘や役割の自動交渉を先に完成させる必要はなく、初期の検証では参加者が合意済みの状況を明示して使います。

## 二つの単位

| 単位 | 管理するもの | 修理の例 |
|---|---|---|
| 作業全体 | 必要な成果、工程の依存関係、保持する進捗 | 診断、部品交換、動作確認 |
| 実行区間 | 実際の参加者、役割、開始と終了、予約、消費、結果 | 技術担当と補助担当が共同で部品を交換する20分間 |

作業全体は個人の行動と複数人の行動を組み合わせられるようにします。診断を一人で行い、重い部品の交換を二人で行い、別の人が確認を担当する構成も同じ形式で表します。並行してよい工程は依存関係で制約せず、同じ人や道具を使う場合は予約で競合を解決します。

一つの実行区間が始まった後は、その参加者・役割・合意内容を固定します。人が抜ける場合は区間を終了または中断し、進捗を保持したまま、別の構成で新しい区間を作ります。作業全体が続くことと、同じ実行区間を再利用することを分けます。

## 現行実装との接続

| 現行の接続先 | 再利用する部分 | 追加または調整する部分 |
|---|---|---|
| [time_kernel.py](../engine/time_kernel.py) | 一方向に進む時刻、区間、境界の順序 | 共同実行の開始と完了を境界へ登録する |
| [action_lifecycle.py](../engine/action_lifecycle.py) | 開始、完了、中断、経過量 | 一つの区間に複数人を束ねる受付と、一度だけ行う決済 |
| [action_timing.py](../engine/action_timing.py) | 所要時間、消費、中断、行動中の扱い | 個人行動と共同行動の時間の競合を共通に確認する |
| [calendar_runtime.py](../engine/calendar_runtime.py) | 作業量、寄与、材料、道具の使用、保存と復元 | 共同区間から同じ作業記録へ寄与を書き込む |
| [calendar_planning.py](../engine/calendar_planning.py) | 作業の依存関係、目的からの探索 | 役割を満たす共同工程を候補に含める |
| [goal_planner.py](../engine/goal_planner.py) | 個人の優先順位、安全確認、再計画 | 他人の参加を条件付き予測にし、自分の参加候補を評価する |
| [social_planning.py](../engine/social_planning.py) | 依頼、受諾、拒否、受信の記録 | 共同実行の合意内容とバージョンに結び付ける |
| [concerns.py](../engine/concerns.py) | 状態の判定、本人が知る範囲 | 作業の参照先を共通の作業記録へ解決する |
| [sim.py](../engine/sim.py) と [verbs.py](../engine/verbs.py) | 既存の選択順、移動の成立条件、実際の効果 | 全参加者の行動枠を確認し、位置などの変更をまとめて確定する |

現在の ActionLifecycle は一人をキーに行動中の情報を保持します。暦の作業管理も個人ごとの行動から作業量を加算しています。ここへ複数人を同じ工程に束ねる入口を追加し、参加者の数だけ完了処理を繰り返す構造を避けます。

行動中かどうかを確認する窓口も共通にします。選択、開始、自然回復、資源の競合、保存と復元は、個人の行動と共同区間への参加の両方を確認します。共同区間を人数分の個人作業として既存の加算処理へ登録しません。

既存の task 条件は暦の実行に限定されています。通常ターンの共同作業へ接続する際は、条件の参照先と書き込み先を同じ作業管理の窓口へ解決する必要があります。暦側と通常ターン側で、同じ作業に二つの進捗記録を作らないことを実装条件にします。

## 設定と実行中の状態

| 置く場所 | 内容 |
|---|---|
| 世界の行動定義 | 役割と人数、役割の資格条件、成立条件、所要時間、資源、消費、進捗の計算、効果、中断時の扱い |
| 世界の作業定義 | 工程と依存関係、必要な作業量、成果物と有効な対象 |
| 人物の設定 | 大切にする目的、優先順位、譲れない条件、既存の行動権限や知識 |
| 実行区間の記録 | 行動定義とバージョン、参加者と役割、合意、実際の開始と終了、予約、消費済みの量、受信者 |
| 作業の実記録 | 実際の進捗、寄与、成果物、適用済みの出来事、対象と入力のバージョン |

行動の定義に物語名や特定の人物名で分岐する処理を置きません。人物名、道具名、場所は実行時に対応付けるデータです。資格条件は既存の行動権限、役割、知識、状態条件を参照します。新しい性格の数値は追加しません。

実行する参加者と、効果を受ける対象は区別します。修理される設備は参加者ではありません。同じ考えで、人を運ぶ場合も、運ばれる対象であることだけを参加の合意として扱いません。

## 共同実行の契約案

契約例は [joint-activities-contract.json](design-examples/joint-activities-contract.json) に置きます。このファイルは実装用の設計資料であり、現在の世界設定として読み込む入力ではありません。

行動定義には provider、roles、duration、location_policy、resources、costs、progress、interruption、effects を持たせます。provider は登録済みの実行処理を指し、任意のプログラムや自由記述の命令は実行しません。

実行区間には instance_id、definition_id、definition_revision、terms_revision、roles、bindings、consents、earliest_start、expires_at を持たせます。合意内容の識別には役割・対象・資源・時間・消費・効果を含めます。その内容が変わればバージョンを更新し、古い合意で新しい内容を実行しません。

世界側の入口は追加予定の joint_activities.version を1とし、定義、工程、明示した初期合意を登録します。項目がない世界は従来の実行経路を使います。公開済みの定義を実行途中で編集した場合は、実行中の区間が参照するバージョンを保持するか、新しいバージョンの区間として成立条件を確認し直します。

同じ人物が一つの区間で二つの人数枠を埋めることは、初版では認めません。一人が別の工程で異なる役割を担うことは認めます。役割の兼務は、同時に二人が必要な作業を一人で成立させる抜け道になり得るため、別の仕様として扱います。

## 状態の遷移

| 状態 | 意味 | 次に進む条件 |
|---|---|---|
| proposed | 内容が提示され、返答を待っている | 必要な人物に内容が届き、同じバージョンへ合意する |
| agreed | 必要な合意がそろった | 開始時点が選べ、全員と資源をまとめて予約できる |
| reserved | 将来の共通の開始時点を確保した | 開始時に権限、所在、体力、個人の条件、資源を再確認する |
| running | 実際に開始し、時間と負担が発生している | 完了条件または中断条件が成立する |
| completed | 実際の効果と決済を一度だけ確定した | 終端状態 |
| canceled | 開始前に拒否、期限切れ、条件変更などで中止した | 終端状態 |
| interrupted | 開始後に継続できなくなった | 終端状態。必要なら別の区間で再開する |

受諾だけでは人物も船も移動せず、材料も消費しません。予約に失敗した場合も、部分的な予約を残さず、開始前の状態として記録します。

中断した区間そのものを running に戻しません。再開は同じ作業と残る進捗を参照する新しい区間にします。個人の目的の達成・失敗はこの状態とは別に既存の目的評価で判断します。

## 時間と予約

共同実行は既存の TimeActionKernel の時刻を使います。所要時間は正の整数と単位を明示し、logical_step と minute を暗黙に変換しません。各区間は開始を含み終了を含まない時間として、人と道具を確保します。

通常ターンでも、共同実行は所要時間付き行動として扱います。例えば朝から1 logical_stepの移動なら、次の境界である昼に完了します。その区間を占める人物は朝の別行動を選ばず、昼の完了後に次の行動を選べます。従来の即時移動の時間を、この仕様へ一括変更しません。

人物の選択順の途中では共同実行を開始しません。必要な合意を受け取った後、全員が空いている次の共通境界へ予約します。現在の境界ですでに行動した人が、同じ枠でもう一度共同実行することを防ぎます。合意が最初から明示されている場合は、初期状態で指定した境界から開始できます。

共同実行を有効にした世界では、経過分の進捗と消費、物理的な完了、予定された外部変化、合意や情報の受信、目的の評価、予約済み区間の開始前の再確認、新しい選択、の境界処理へ接続します。物理的な完了は同時刻の期限判定より先に扱います。完了と破壊が同時刻なら完了を先にするという、既存の暦の規則に合わせます。

通常ターンの既存処理は予定された出来事と所要時間付き行動の完了を一つの処理で扱っています。この処理を分割して共同実行の境界へ接続する必要があります。有効化していない世界の順序や保存済みの記録は変えず、有効化した場合の順序は新しい実行契約として固定します。既存の暦の途中の評価処理も維持し、共同区間の開始を、必要な受信が終わる前に置かないことを条件にします。

予約は全員・全資源をまとめて成功させます。個人行動、暦の仕事、通信に使っている時間も同じ空き時間の確認へ含めます。一部だけ押さえたまま他を待つ予約は作りません。予約には有限の開始期限を設け、拒否や期限切れで解放します。

競合する予約を同じ人へ勝手に割り当てません。本人が既存の優先順位と譲れない条件で選びます。同等の場合の並び順は再現可能な順序に固定し、物語名を判断材料にしません。

観測期間外に完了する予約は初版では開始候補から除外します。特に通常ターンの最後の境界で、正の所要時間を持つ行動を即時完了扱いにしません。長時間の未完了行動を期間外へ保存する拡張は、別途同じ時刻規則で設計します。

## 進捗と費用

作業には一つの実記録と、一つの書き込み権限を割り当てます。既存の暦の作業であれば、その作業記録が実記録です。共同実行は同じ記録へ、区間の識別子と寄与を渡して加算します。通常ターンの作業も同じ窓口を通して管理します。

作業量の計算は初版では fixed_group_rate と sum_role_rates の二つに限定します。前者は必要な役割がそろった間だけ、集団として一定量進む方式です。後者は役割ごとの寄与を足す方式で、必要なら上限を設定します。二人で一つの部品を支える作業を、二倍の進捗として数えないための区別です。

実際の消費と寄与は人物ごとに記録します。操船者は体力を使い、同乗者は同じ時間を使っても体力消費を0にするなど、役割ごとに定義できます。時間、体力、成果への寄与は同じ数値とは限りません。

数値は既存の暦の体力計算と整合する有理数として保持します。進捗を加える際は前回の確定時刻からの差だけを使い、同じ境界の再処理で再加算しません。新しい共同計算へ接続した作業では、従来の個人用の加算処理を重ねて実行しないことを条件にします。

材料は開始時または完了時のどちらで消費するかを定義します。開始時に消費した材料は中断で自動的に元へ戻しません。完了時に消費する材料はそれまでは予約数量を他の予定へ二重に割り当てないようにします。予約は盗難や破壊から物を保護する物理効果ではありません。実際に物が失われれば、開始条件または継続条件を再評価します。

## 位置と道具の効果

共同移動では、参加者全員の経路、行動範囲、除外条件、移動許可を確認し、共有する乗り物の使用条件を集団に対して確認します。船が同じ渡航区間で使用中であることを、乗船場所にまだ残っていることと混同しません。通常の個人移動の道具の使用条件は維持します。

開始時には全員を同じ移動区間へ所属させ、移動中として扱います。到着時には全員の位置と必要な資源の決済を一つの取引として確定します。人物ごとに移動処理を順番に呼び、途中までの位置変更を他の人物が見る構造にはしません。既存の移動処理から、条件確認と位置変更を分離して再利用します。

正の所要時間を持つ移動には、移動中の実際の場所を定義します。単一区間の例では transit_zone を使い、必要なら経路上の区間ごとに場所を定義します。外部の破壊や強制中断が起きた場合、その時点に対応する場所へ全員の状態を確定し、出発地や目的地へ自動で戻しません。移動中の場所が未定義の契約は受け付けません。

同じ船や工具は、同じ物を表す共通の資源参照に結び付けます。複数の別名で同じ物を二重予約できる設定は拒否します。資源の実際の持ち主や数量が変われば、古い予約内容を再確認します。

作業の成果物は一度だけ作ります。参加者全員へ同じ一個の部品を複製して渡しません。完成品の持ち主や置き場所も行動の効果として指定します。

## 中断と引き継ぎ

| 状況 | 扱い |
|---|---|
| 開始前に一人が断る | 必須人数と役割を確認し、開始しないか別の構成を提案する |
| 開始時に体力が足りない | 全員の開始を中止し、開始に伴う費用は取らない |
| 任意の役割が離脱する | 現在の区間を確定し、残る役割と合意を確認して次の区間を作る |
| 必須の役割が欠ける | その時点までの寄与を記録して中断する |
| 代役が参加する | 新しい合意と区間で、同じ作業の残量を進める |
| 診断者が離れる | 成果を保持する。次の担当者が必要な診断内容を受け取ったかは別に確認する |
| 対象そのものが交換される | 成果の対象とバージョンを確認し、適合しない成果を自動で流用しない |
| 船や道具が破壊される | 物理的な変化を適用し、所在・消費・進捗を残して継続可否を判定する |

能動的な離脱を許す時点は行動ごとに定めます。航行中に下船できる条件と、作業台から離れられる条件は異なります。能動的な離脱を制限する設定でも、死亡や道具の破壊などの物理変化は無視しません。

引き継ぐのは実際の作業成果です。作業が終わったという出来事を知ることと、診断の内容や手順を知ることは別に記録します。必要な情報が届いていない代役は、既存の情報取得や共有を計画します。

## 人物の目的と知識

参加候補は、本人が知る合意内容・状況・能力・消費見込みを用いて、既存の目的評価へ渡します。高い優先順位や譲れない条件に反する参加を、主催者の都合で確定しません。参加した事実だけで、共通の最終目的を人物へ追加することもありません。

仲間がいるという設定だけで、主催者が常に共同移動を選ぶ扱いにはしません。共同移動を選ぶ根拠も同行者の支援や合意を守ることなど、本人の目的へ結び付けます。合意済みの初期入力から実行を確かめる試験と、人物が自分で共同移動を選ぶ試験は分けます。

主催者の計画では、他人の返事、将来の所在、将来の資源の確保を条件付きの見込みとして扱います。実際の予約は実行側の処理でのみ行い、探索だけで他人を行動中にしたり、道具を予約したりしません。

合意の返答は、届いた相手だけが知ります。実際に参加する人物には自分の区間と役割を知らせ、乗船や作業を目撃した人物には、見えた出来事だけを知らせます。遠くの人物の目的や、拒否した秘密の理由を公開しません。

共同移動中の「同じ場所にいる」と「目的地に到着した」は区別します。同じ乗り物の内部にいる実際の参加者には、その場の観測を渡します。既存の co_location 条件には、その根拠も接続します。zone 条件は移動中であるだけでは目的地への到着を満たしません。

同じ航路の名前を使っていても、別の乗り物の内部は自動で見えません。また、遠隔で行う共同作業では、同じ作業への参加だけで所在や知識を共有しません。位置の条件が参照する座標と、本人へ渡す観測に、区間と乗り物の所属も含めて整合させます。

途中の失敗は既存の再計画の原因として記録します。予約できなかったことや作業を中断したことを、物語全体の目的の失敗確定と同一視しません。実際に確定した目的の終端記録は、共同作業を再開しても消しません。

## 保存と復元

共同区間の管理用の記録は一つだけ保存し、人物ごとの行動中の情報にはその区間への参照と役割を持たせます。全員の参照、区間、予約、消費、作業進捗がそろった状態を、一つの境界の保存単位にします。

記録には世界と定義のバージョン、合意内容、参加者、予約、開始と終了、消費済みの量、進捗を確定した時刻、適用済みの効果、受信者を含めます。復元は保存した状態を読み戻すだけで、受諾、消費、移動、完成品の発生をもう一度実行しません。

効果の識別子は区間と段階に結び付けます。人物別の表示記録から再び実行することを禁止します。同じ完了通知が届いても効果は一度です。参加者の参照の欠落、予約の不一致、確定時刻の逆戻り、世界のバージョンの不一致があれば、復元を止めます。

実装上の例外ではその境界の書き込みをまとめて戻します。世界内で実際に起きた事故や中断では、時間と物理的な結果を戻しません。

## 記録と画面

共同区間には一つの原記録を作り、人物別の記録は同じ区間を参照します。共同区間の状態、作業全体の進捗、人物の目的の判定を別々に表示します。

一覧では行動名、参加者と役割、開始と終了、作業の残量を示します。詳細では参加を判断した理由、待っている役割、資源の競合、中断の原因、個人の負担、実際の成果と受信者を確認できるようにします。未回答を受諾済みと表示しません。

画面の実装は [ui-design.md](ui-design.md) と既存の「目的と計画」に合わせます。新しい専用の画面体系は作らず、共同行動を一つのまとまりとして表示し、人物ごとの内訳へ移動できる構成にします。

## 契約例の読み方

船の例は、操船者一人と同乗者三人が一隻を使い、同じ区間を移動する構成です。操船者だけが体力を消費し、全員が同じ時間を使います。移動中の場所は航路として明示します。

修理の例は診断、共同での部品交換、動作確認からなる構成です。診断内容は実際の情報共有で交換担当へ渡します。交換の進捗は集団として毎分1、技術担当と補助担当の体力消費は別々です。二人が参加しても進捗を毎分2へ増やしません。診断者は交換中に別の行動を取れます。

交換の途中で必要な人が離れた場合は、進めた作業量を残します。新しい担当者が同意して再開すれば、残量だけ進めます。修理済みという最終効果は、動作確認まで実際に完了してから確定します。

## 初版の上限と失敗時の扱い

初版の仮の上限は、一つの区間に16人、役割は8種類、行動定義と作業工程はそれぞれ32件とします。必須の人数は合計1人以上16人以下とし、同じ区間へ割り当てる人数の上限も確認します。役割候補の組み合わせは最大256件までを、既存の探索全体の上限の内側で調べます。上限に達した場合は探索の打ち切りとして記録し、成立不能や目的の失敗と断定しません。

未知の provider、循環する工程、単位の混在、同一人物の重複、資源の別名による二重予約、バージョンの違う合意、負の費用や進捗、観測範囲外の時刻は検証で拒否します。任意の式を評価する設定や、他人の内部状態を直接読む予測は認めません。

## 実装する窓口

以下は追加予定の実装単位です。窓口の名前と責任を固定し、既存の処理を物語別に複製しない方針にします。

| 追加する単位 | 主な操作 | 責任 |
|---|---|---|
| engine/joint_activities.py | propose、record_consent、reserve、start_due、advance、interrupt、restore | 契約のバージョン、共同区間の管理用の記録、状態の遷移、効果の一度だけの確定 |
| engine/activity_bookings.py | reserve_all、release、is_busy、validate | 人と道具の時間の競合を、個人の実行処理も含めて確認する |
| engine/work_registry.py | bind_store、read、commit_progress、commit_completion | 作業ごとに管理用の記録の保存先と書き込み担当を一つにし、既存の作業へ接続する |
| engine/joint_planning.py | candidates、steps、relevant_coordinates、observe | 既存の計画探索へ共同工程の候補と条件付き予測を提供する |

個人の pending と共同区間の記録は、それぞれ元の実行処理が保持し、予約と行動中の共通の窓口から参照します。個人行動の開始・完了・中断にも予約との照合を接続し、共同参加中の人物が自然回復や別の行動の判定から抜け落ちないようにします。

作業の定義と参照は世界の読み込み時に結び付け、実際の作業記録は実行環境を接続した時に結び付けます。実記録の接続前に進捗を0と推測しません。暦の作業の加算処理は共同区間を受け持つ場合に既存の個人用の加算対象から外し、同じ進捗を二つの経路で更新しません。

共同の計画候補は既存の通常ターン用・暦用の候補へ加えます。既存のドメインを共同用のドメインへ置き換えて、個人の移動・作業・休息の候補を失わないようにします。参加者ごとの開始前の評価と、実際の資源確認は実行側で再実施します。

## 実装の順序

| 順序 | 実装するもの | 完了の条件 |
|---|---|---|
| 1 | 共通の型と作業記録の窓口 | 契約、役割、対象、バージョン、既存の作業への参照を検証できる |
| 2 | 複数人と資源の予約および時間管理 | 個人行動との競合、開始時の再確認、全員の時間の消費、保存と復元を扱える |
| 3 | 共同移動の実行処理 | 一隻で全員が移動し、位置と費用が一度だけ確定する |
| 4 | 共同作業と段階的な進捗 | 複数人の寄与、途中の離脱、引き継ぎ、成果物の一度だけの発生を扱える |
| 5 | 個人の目的評価と計画への接続 | 各人の受諾・拒否・別の目的の優先と、条件付き予測を扱える |
| 6 | 記録と表示および物語の比較 | 原記録から共同区間と人物別の経過を追え、別題材でも実行できる |

受入条件は [joint-activities-acceptance.md](joint-activities-acceptance.md) に定めます。最初から移動と修理の契約を同じ型で表し、どちらか一方にだけ通用する構造になっていないことを各段階で確認します。
